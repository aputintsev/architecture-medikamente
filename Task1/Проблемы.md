# Проблемы системы

## 1. Хранение 
Данные хранятся в открытом виде на общем диске в виде файлов Excel и сканов JPG/PDF. 1С работает в файловом режиме и располагается на том же файловом сервере, что и остальные данные. Это создает критический риск, поскольку отсутствует разграничение доступа на уровне записи/строки. Любой сотрудник с доступом к папке видит все сканы всех пациентов. Данные не шифруются at rest.

## 2. Нарушен принцип Data Minimization 
При регистрации собирается расширенная анкета, содержащая множество чувствительных данных, не всегда нужных в контексте конкретного случая. Вкупе с упомянутой выше проблемой хранения, это может привести к повышенному ущербу и дополнительным рискам.

## 3. Контроль доступа
Реализована только доменная аутентификация на базе Active Directory. Отсутствует RBAC/ABAC. Невозможно отследить, кто смотрел карту конкретного пациента. Нет аудита действий с файлами.

## 4. Передача данных
Обмен файлами с данными пациентов ведется по сети. Также есть интеграция 1С и ККМ через OLE. Все данные передаются по незащищенным каналам . Отсутствует шифрование данных в транспорте внутри периметра. В текущем виде не получится интегрироваться с лабораториями через API.

## 5. Аудит и Мониторинг
Отсутствует. Нет возможности отслеживать кто осуществляет действия с файлами. Также нет возможности ведения журнала чтения/записи в ячейки и строки Excel-таблиц. Как следствие, невозможно расследовать потенциальные инциденты утечек. Это нарушает требования 152-ФЗ.

## 6. Удаление данных
Для удаления необходимо вручную стирать файлы с диска, что не гарантирует невозможности их восстановления. Как следствие, требование прекратить обработку данных по запросу клиента технически сложно выполнить из-за разрозненности файлов и бэкапов.

## 8. Data Lineage
Происхождение данных не отслеживается. Копирование файлов невозможно контролировать. Как следствие, невозможно определить первоисточник данных и все места распространения данных пациента.

# Классификация данных и методы защиты

| Категория данных    | Примеры                                    | Способ защиты                 | Техническая реализация                                                                                                                                 |
|---------------------|--------------------------------------------|-------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------|
| Персональные данные | ФИО, Дата рождения, Телефон, Email         | Шифрование                    | AES-256 в БД (PostgreSQL pgcrypto или прозрачное шифрование на уровне файловой системы). Для поиска — хеширование (HMAC/SHA-256) в отдельных индексах. |

Все данные также должны шифроваться при передаче между сервисами.

# Тегирование данных

## По типу данных
Эти теги позволяют разграничить уровень доступа и интегрировать его с RBAC-моделью 

- PII - персональные данные
- PHI - медицинские данные
- FIN - финансовые данные
- PII_DOC - сканы документов
- SUP - данные поставщиков

## Служебные теги
Это теги, предназначенные для автоматизации процесса аудита и удаления данных.

- LIFECYCLE_RETENTION_3Y - эти данные должны удаляться через 3 года
- LIFECYCLE_DELETE_ON_REQUEST - пометка для автоматики, что такие данные должны быть автоматически уничтожены по запросу от клиента
- ACCESS_AUDIT_L1 - базовый уровень аудита. Логируется только факт изменения/записи (например, расписание врача).
- ACCESS_AUDIT_L3 - полный уровень аудита. Каждое чтение этой сущности логируется в SIEM (например, диагноз).
